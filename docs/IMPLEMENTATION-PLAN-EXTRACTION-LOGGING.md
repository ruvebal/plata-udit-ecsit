# Confluence-Style Implementation Plan: Automated Extraction Logging and Performance Analysis

**Project:** PLATA Extract (`plata-extract`)  
**Owner:** ECSIT / UDIT  
**Status:** Proposed  
**Target Version:** 0.2.x  
**Document Type:** Implementation Plan for AI Agent Execution

---

## 1. Executive Summary

Today `extract.log` is created manually after runs. This is error-prone, inconsistent, and loses critical runtime context (exact command, config, stage timings, retries, warnings, failures, and environment).

This plan introduces **automatic run logging** generated by the extraction pipeline itself, with two outputs:

1. **Human log** (`extract.log`) for researchers and quick review.
2. **Structured event log** (`extract.events.jsonl`) for reproducible analysis, benchmarking, and dashboards.

The logging feature must be backend-agnostic (`plain`, `plain-docling`, `neural`) and include actionable best-practice diagnostics.

---

## 2. Problem Statement

### Current pain points

- Manual logs are incomplete and inconsistent between runs.
- No standard format for performance comparison.
- Hard to distinguish extraction quality issues vs. backend/runtime failures.
- Hard to reproduce command context (flags, env, versions, device).
- Shell output is not systematically captured with extraction events.

### Business/Research impact

- Low confidence in reproducibility of extraction experiments.
- Difficult to compare backends for speed/quality trade-offs.
- Difficult to build a robust corpus ingestion quality process.

---

## 3. Goals and Non-Goals

### Goals

- Auto-generate `extract.log` for every run (single and batch).
- Auto-generate structured machine-readable logs for analysis.
- Capture command context and key runtime metadata.
- Capture stage-level timings and failure diagnostics.
- Provide stable schema for future analytics scripts.
- Document rationale and usage in README and troubleshooting docs.

### Non-Goals (v1)

- No external observability stack (ELK, OpenTelemetry, Prometheus).
- No live dashboard in this phase.
- No heavy profiling overhead by default.

---

## 4. Decision: Log Format and Storage

### 4.1 Output files (per document output directory)

For each extracted document folder (`exports/<DOC>/`):

- `extract.log` (human-readable, plain text)
- `extract.events.jsonl` (structured events, one JSON object per line)
- optional future: `extract.summary.json` (compact run summary)

For batch mode (`input` is directory), add run-level logs under output root:

- `exports/_runs/<RUN_ID>/run.log`
- `exports/_runs/<RUN_ID>/run.events.jsonl`
- `exports/_runs/<RUN_ID>/run.summary.json`

### 4.2 Why dual format

- `extract.log` is best for quick human reading and support tickets.
- `extract.events.jsonl` is best for deterministic parsing and KPI automation.

This gives both researcher usability and engineering reliability.

## 5. Proposed Log Schema

### 5.1 Core metadata fields (required in first event)

- `run_id` (uuid4)
- `timestamp_utc`
- `plata_extract_version`
- `python_version`
- `os_name`, `os_version`, `arch`
- `backend` (`plain|plain-docling|neural`)
- `input_path`, `output_dir`
- `command_argv` (full argv list)
- `command_string` (shell-safe joined command)
- `flags` (parsed args snapshot)
- `env_subset` (safe whitelist only)

### 5.2 Safe env whitelist (do not leak secrets)

Allow only keys like:

- `TORCH_DEVICE`
- `OLLAMA_HOST`
- `OLLAMA_NUM_PARALLEL`
- `OLLAMA_KEEP_ALIVE`
- `PYTHONPATH`

Never log API keys, tokens, or full environment dump.

### 5.3 Event types (minimum)

- `run_started`
- `pdf_check_started`
- `pdf_check_completed`
- `extract_started`
- `stage_completed` (layout/ocr/tables/write where available)
- `warning`
- `error`
- `extract_completed`
- `run_completed`

### 5.4 Performance fields

- `elapsed_ms`
- `page_count`
- `word_count`
- `image_count`
- `pages_processed`
- `throughput_pages_per_sec`
- `backend_substage` (if known)
- `llm_requests`, `llm_tokens_used`, `llm_errors` (if available)

### 5.5 Error fields

- `error_type`
- `error_message`
- `traceback` (trimmed; full only in debug)
- `suggested_action`
- `is_retryable` (bool)

## 6. Human Log (`extract.log`) Format

### 6.1 Header block

- Command
- Backend + flags
- Start/end times
- Duration
- Versions (plata, python, key libs)
- Device selection (`mps`, `cpu`, etc.)

### 6.2 Body block

- Integrity check result
- Stage timings summary
- Warnings/errors with context
- Output artifacts paths

### 6.3 Footer block

- KPIs: pages/sec, words/sec, images/page
- Verdict: `SUCCESS`, `PARTIAL`, `FAILED`
- Recommendation section (automatic heuristics)

Example recommendations:

- "Neural failed with AcceleratorError; consider `TORCH_DEVICE=cpu`"
- "LLM timeout rate high; increase Ollama timeout/model speed"

## 7. Shell Output Capture Strategy

### Problem

Some runtime details are emitted to stdout/stderr by dependencies (progress bars, warnings).

### Decision

Capture shell output in a controlled way **inside the app process**:

- Route Python logger to both console and file handlers.
- Capture warnings module output and redirect to logger.
- Do **not** blindly redirect all stderr globally (to avoid breaking CLI UX).
- For dependency prints that bypass logging, use a scoped capture context around extraction call and append to `extract.log` under `Raw Runtime Output` section.

### Rationale

- Preserves interactive user experience.
- Still persists critical runtime lines for audit.
- Avoids coupling to terminal/IDE behavior.

## 8. Code Architecture and Integration Points

### 8.1 New modules

- `plata_extract/logging_schema.py`
  - Typed dataclasses / TypedDict for events.
- `plata_extract/run_logger.py`
  - `RunLogger` class: writes human and jsonl logs.
- `plata_extract/runtime_capture.py`
  - Optional scoped stdout/stderr capture utilities.

### 8.2 Existing files to update

- `plata_extract/cli.py`
  - Create `run_id` and initialize `RunLogger`.
  - Emit run-level events for single/batch.
- `plata_extract/extract.py`
- `plata_extract/extract_plain.py`
- `plata_extract/extract_plain_docling.py`
  - Emit extraction stage and result events.
- `plata_extract/check.py`
  - Emit check start/complete/fail events.

### 8.3 Backward compatibility

- Keep current stdout behavior unchanged.
- Logging defaults enabled; optional `--no-log` can disable file logs.

## 9. CLI Additions

Add flags:

- `--log-level {info,debug,warning,error}` (default `info`)
- `--log-jsonl` (default `true`)
- `--log-dir PATH` (default document output dir / `_runs/<run_id>`)
- `--no-log` (disable all file logging)

Optional future:

- `--profile` (adds extended timing/resource metrics)

## 10. Best Practices for Result and Performance Analysis

### 10.1 KPI definitions

Primary:

- `success_rate = successful_docs / total_docs`
- `pages_per_sec = pages_processed / elapsed_sec`
- `mean_time_per_page`
- `llm_error_rate = llm_errors / llm_requests`

Quality proxies:

- `images_per_page`
- `word_count_per_page`
- `empty_page_ratio`
- `ocr_warning_count`

Stability:

- `accelerator_error_count`
- `timeout_count`
- `retry_success_rate`

### 10.2 Baseline and comparison workflow

1. Run same PDF set with each backend.
2. Export and aggregate JSONL events.
3. Compare KPIs by backend and document class.
4. Flag regressions >10% in throughput or >5% in failure rate.

### 10.3 Suggested analysis script (future)

Create `scripts/analyze_logs.py` to read `extract.events.jsonl` and output:

- CSV summary
- Markdown report
- Simple trend chart data

---

## 11. Reliability and Security Requirements

- Logs must never contain secrets.
- File writes must be atomic where possible.
- Logging must never crash extraction flow.
- If logging fails, continue extraction and emit warning to console.
- JSONL events must be schema-validated before write in debug mode.

---

## 12. Testing Plan

### Unit tests

- Event schema validation.
- Human log formatter output.
- Safe env whitelist filtering.
- Error serialization with traceback trimming.

### Integration tests

- Single-file run writes both log formats.
- Batch run writes run-level and file-level logs.
- Failures still produce complete logs.
- `--no-log` produces no log files.

### Regression tests

- Existing CLI output unchanged.
- No measurable slowdown >3% with logging enabled.

## 15. Acceptance Criteria

The feature is complete when:

1. Every extraction run auto-generates `extract.log` and `extract.events.jsonl`.
2. Logs include command, backend, versions, timing, output paths, and errors.
3. Batch mode produces run-level summary logs under `_runs/<run_id>`.
4. README and TROUBLESHOOTING explain rationale and usage.
5. Automated tests cover success, failure, and disabled logging paths.
6. No secrets are present in logs.

---

## 16. Implementation Notes for AI Coding Agent

- Prefer additive changes; do not break current extractor contracts.
- Keep logging side effects isolated in a dedicated module.
- Use strict typing and small pure functions for formatters.
- Guard all log writes with exception-safe wrappers.
- Preserve user-facing CLI speed and readability.
- Add concise comments explaining why each logging decision exists.

---

## 17. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Log verbosity too high | Large files, noise | Tiered levels + concise defaults |
| Sensitive data leakage | Security issue | Env whitelist + redaction pass |
| Performance overhead | Slower extraction | Buffered writes + minimal default events |
| Inconsistent events across backends | Hard analysis | Shared schema + backend-specific optional fields |
